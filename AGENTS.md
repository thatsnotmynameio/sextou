# AGENTS.md

Guidance for coding agents working in this repository. Claude Code reads it as `CLAUDE.md`, a symlink to this file.

sextou is a web app, the Electron desktop app that loads it, and the remote server they talk to: React and TypeScript, in a pnpm monorepo.

Write every report, summary, or handoff to the user through the `ce-noslop` skill. This applies when you are the top-level agent writing to the user, not when you are a subagent reporting to its caller. Do not apply it to code, config, verbatim quotes, or text the user asked to post as written.

After a solved, verified problem, automatically invoke the `ce-compound` skill with `mode:non-interactive` at the completion checkpoint only when the work produced durable project reasoning that is not readily recoverable from the final code, tests, types, comments, or existing documentation, and losing it would plausibly cause recurrence, material risk, or substantial rediscovery. Apply this counterfactual: if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? If not, do not invoke it. Completion, effort, and diff size alone are not enough. Capture at the checkpoint so a qualifying learning can ship in the PR that produced it, and only where the repository treats captured learnings as tracked, committed knowledge.

## Commands

Run every command from the repository root. Use pnpm, never npm.

```sh
pnpm install
pnpm lint             # oxlint, then oxfmt --check
pnpm lint:fix         # both, fixing what they can
pnpm typecheck        # tsc --noEmit in each package
pnpm test:unit        # every unit suite, with coverage
pnpm test:integration # every integration suite, with coverage
pnpm test:component   # packages/ui's stories in Chromium (Playwright), with coverage
pnpm test             # each package's levels in turn: unit, integration, component
pnpm --filter <package> test:<level>   # one level of one package, such as @sextou/tasks test:integration
pnpm --filter <package> test           # every level of one package
pnpm --filter <package> test:mutation  # Stryker over the package's unit and integration suites; fails below 80% of mutants killed
pnpm exec vitest run --project '<pkg>/*' <path> # one module's unit and integration tests, such as 'server/*' modules/health, with no coverage verdict
pnpm build            # electron-forge package, the web app, storybook build, then the server's and the runner's bundles
pnpm start            # the web dev server and the desktop app, in development
pnpm storybook        # Storybook at http://localhost:6006
pnpm --filter @sextou/server dev # the server from source, at http://127.0.0.1:4310
```

`pnpm start`, `pnpm storybook` and the server's `dev` start long-running processes: leave them to the user. Neither `pnpm start` nor the desktop app starts the server: the web app talks to the one at `SEXTOU_WEB_SERVER_URL`. Each app reads its settings from environment variables with defaults, listed in its `.env.example`; a `.env` beside it changes them in development.

## Architecture

- `apps/web` (`@sextou/web`): the React app, built by its own Vite config into `apps/web/dist`. It talks to the server through the tRPC client, at the URL it was built with (`SEXTOU_WEB_SERVER_URL`), and takes nothing from the server but its router's type. It reaches native features only through web APIs, which Electron maps to native ones in the desktop window, and through what the preload exposes. Lint fails on an `electron` import in `apps/web` or `packages/ui`.
- `apps/desktop/src/main`: Electron's main process. Bundled by Vite into `.vite/build/main.cjs`.
- `apps/desktop/src/preload`: the preload script, the only bridge between main and the web app (`contextBridge`).
- `packages/ui` (`@sextou/ui`): shared React components, each in `src/<Name>/` with `<Name>.tsx` and `<Name>.stories.tsx`, its test in `tests/unit/<Name>/<Name>.test.tsx`, exported from `src/index.ts`. It ships sources, not a build: each app's Vite compiles it. Components take data and callbacks as props and never touch Electron, so they render in Storybook and in any app.
- The desktop loads the hosted web app by URL instead of bundling its build, from `SEXTOU_WEB_URL`, which `vite.main.config.mts` reads: in development from the environment or `apps/desktop/.env`, `apps/web`'s dev server (`http://localhost:5173`) by default; in production the deployed URL, from the environment at package time. When the URL can't load, the window shows the error page in `src/main/error-page.ts`, bundled into `main.cjs`. A web deploy reaches desktop users on their next reload; only shell changes (Electron, preload, native features) need a desktop release.
- Forge's Vite plugin packages only `.vite/`: everything the shell runs (main, preload, the error page) must be bundled.
- The backend is two packages, and dependencies point one way: `@sextou/server` imports `@sextou/tasks` only in its tasks service (`src/tasks-service.ts`), the web app imports the server's router type, and `@sextou/tasks` imports no other sextou package. `@sextou/server` and `@sextou/runner` both import `@sextou/logger` and `@sextou/config`, which import no other sextou package either. CI's knip fails on an import a package doesn't declare.
  - `apps/server` (`@sextou/server`): the HTTP server, its own process, which runs remotely; a local server is one a developer starts. Hono serves its tRPC router at `/trpc`, and CORS lets only the web app's origin (`SEXTOU_SERVER_WEB_ORIGIN`) read the answers. Each procedure's output is checked against its zod schema before it is sent. Its database is a SQLite file, or `:memory:`, through drizzle (`drizzle-orm`, pinned to a release candidate, the only one with a Turso driver) and Turso's async API (`@tursodatabase/database`, pinned, as `@sextou/tasks`'s), with no layer for swapping databases. Turso connects on the first query, so the server starts whatever the file's state, and health reports the database down when it can't open it. `src/config.ts` reads every setting from the environment, and `main.ts` creates the database's folder, starts the tasks service on the tasks database (`SEXTOU_SERVER_TASKS_DB`, `tasks.db` in the data folder by default), then listens; it exits with 1 without listening when a variable is invalid. The data folder (`SEXTOU_SERVER_DATA_DIR`) defaults to `apps/server/storage` from source, left out of the repository, so each checkout and worktree has its own databases, and to the user's data directory in the bundle, which `main.ts` tells from source by `__TASKS_MIGRATIONS__`. An agent that starts the server to check a change uses the `run-server` skill's driver, which gives each start databases in a new temporary folder. It logs through one Pino logger, from `@sextou/logger`'s `createLogger`, which writes one JSON record per line to stdout at the level `SEXTOU_SERVER_LOG_LEVEL` sets, or readable lines through pino-pretty when `SEXTOU_SERVER_DEV` is `true`; a process that starts the server reads the URL from the record whose `msg` is `listening`. The tasks service hands that logger to `openTasks`. A tasks database that doesn't open doesn't stop the server: `main.ts` logs why, and each call to the service rejects until the server restarts. `tasks.link` makes an open task wait for a blocker until the blocker succeeded or was skipped, and `tasks.unlink` stops it waiting, as for a blocker that failed or was cancelled, which holds the task until the link is removed; a task as its own blocker fails with `BAD_REQUEST` and a link that would close a cycle with `CONFLICT`, each with the reason as the message. A task is ready as soon as it is created, so a caller that needs a new task to wait creates it under an assignee no runner serves, links it, then hands it to its real assignee with `tasks.assign`. Runners take tasks through the `runners` procedures: `runners.claim` hands a runner the most urgent ready task of the assignees it serves under a lease (`SEXTOU_SERVER_LEASE_MS`), as the task's id, its `uses` split into where the Taskfile the runner runs lives (`{ repo, sha, taskfile }`: a public GitHub repository, a full commit SHA and the Taskfile's path in it), `null` for a task that names none, which is claimed like any other and fails at the runner, and the task's context, `runners.heartbeat` renews it for the lease the server has now and says whether someone asked to cancel the task, and `runners.complete` ends the task, with the text of the tasks file a run that succeeded left, and answers the outcome the task took, its reason and the id of each task the file created by its key in the file, each logged as a `task created` record; both fail with `CONFLICT` and the message `lease_lost` for an attempt that lost its lease. A file `@sextou/tasks` can't take fails the task, so the outcome answered may differ from the one sent; the server passes it the limits of one file, `SEXTOU_SERVER_MAX_CREATED_TASKS` tasks (50) and `SEXTOU_SERVER_MAX_TASK_DEPTH` parents above each (20). A runner sends a call again as it was when the answer didn't arrive: a claim carries the runner's own `claimId`, which gets the same attempt back, the same completion gets the answer the first got, and the same cancel succeeds once more. A call the tasks database doesn't serve within `SEXTOU_SERVER_TASKS_TIMEOUT_MS` fails with `TIMEOUT`, having written nothing. Once the tasks database opened, `main.ts` starts a sweep (`src/lease-sweep.ts`) that ends the attempts whose lease expired every `SEXTOU_SERVER_LEASE_SWEEP_MS`: the task is cancelled when someone asked to cancel it, else opens again while `SEXTOU_SERVER_MAX_ATTEMPTS` allows, else fails. The leases live in the tasks database, so a restart loses none: the sweep ends no lease until the server has been up a whole lease, and waits a whole lease again after a sweep that ran later than a third of a lease, as when the host slept, so the runners renew first. On SIGINT or SIGTERM it stops listening, then the sweep, then the tasks service, then closes the database. Turso refuses a second process on the same file, so the server runs as one instance per database and per tasks database. Vite bundles it into `apps/server/dist/server.mjs`, with every dependency inlined but Turso, a native addon, and Pino with pino-pretty, which load files at run time: the bundle runs with Node and those packages installed, Turso's for its platform. The server declares Turso; Pino and pino-pretty come from `@sextou/logger`, whose versions are the only ones in the repository. The bundle inlines `@sextou/tasks`'s code but not its migrations, so the build copies `packages/tasks/drizzle` to `dist/drizzle`, and `main.ts` hands that folder to the tasks service; ship it beside `server.mjs`. Turso publishes it for Linux x64 and arm64 with glibc, macOS on Apple silicon and Windows x64, so the server doesn't run on an Intel Mac or on musl Linux (Alpine).
  - `packages/tasks` (`@sextou/tasks`): the task graph, written as a library sextou imports: it knows tasks and their `blocked_by` links, never an organization, and imports no sextou package; Turso (`@tursodatabase/database`, pinned), drizzle (`drizzle-orm`, pinned, as the server's) and zod are its runtime dependencies. Each operation checks its input against a zod schema it exports (`src/schemas.ts`), and refuses an input the schema rejects with the reason `invalid`. A task may carry a `uses`, `owner/name/path/to/Taskfile.yml@<sha>`, the Taskfile a runner runs for it: `createTask` refuses one whose ref isn't a full commit SHA, or whose owner, name or path holds an empty, `.` or `..` part, and `splitUses` splits a stored one into its repository, commit and path. Its tables are declared in drizzle's schema (`src/schema.ts`), and drizzle-kit generates their migrations into `drizzle/` from it (`pnpm --filter @sextou/tasks exec drizzle-kit generate --name <change>`); a test fails when the schema changes without one. Never edit a generated migration. `openTasks(path, { logger })` opens the SQLite file its caller names in WAL mode, through Turso's async API and drizzle, and applies the migrations the file lacks with drizzle's migrator, which reads them from the package's `drizzle/` folder, or from the copy a caller's bundle carries (`migrationsFolder`). Every query goes through drizzle's builder except two recursive queries the builder can't write, the cycle check and a task's depth, the parents above it up `parent_id`, which are drizzle's `sql`. Its caller injects the `logger`, any object with Pino's six level methods (the package's `Logger` type), so the package depends on no logging library; nothing in it logs yet. Every operation returns a promise. Every write is one drizzle `db.transaction()` with `behavior: 'immediate'`, which holds the connection until it commits or rolls back, so another call waits for it, and one that takes the lock or ends past `openTasks`'s `timeoutMs` rolls back and is refused as `timeout`; the write keeps each task's count of the blockers that still hold it (open, running, failed or cancelled) in step, so the ready list reads one partial index (`task_ready`) and the cycle check walks only open and cancelled tasks. Each start of a task is an attempt, a row of `task_executions` whose id is a token: its lease (`expires_at`) is set while it runs, `claimTask` starts the next ready task in one write, and only a call carrying the current attempt's id renews the lease or finishes the task, so one who lost it can't overwrite a later attempt. `finishTask` as succeeded may carry the text of a tasks file, JSON whose `tasks` lists what `createTask` takes but the parent and the creator, under `tasks.create`'s names, each with a `key` and the keys it waits for (`blockedBy`), read by `tasksFileSchema`, which refuses a field it doesn't define: in the same write it creates them as the task's children, recorded as the finisher's, links them, and makes each open task that waited for the task wait for the file's final tasks too, those no other in the file waits for. A file it can't take (not JSON, refused by the schema, a repeated key, a blocker no task in it has or named twice, a cycle, more than the call's `maxTasks`, or tasks deeper than its `maxDepth`) fails the task with a reason that names the task by its key or position and never quotes the file, and creates nothing; when someone asked to cancel the task, a file that holds tasks, or doesn't read as one, cancels it instead, and a blank text or an empty list creates nothing. A claim, a finish or a cancel sent again after its answer was lost gets the answer it would have had: the claim by its actor's `claimId`, the finish when its attempt's digest of the finish that ended it matches, with the tasks it created (`task_execution_tasks`), and the cancel when it matches the task's last change. `expireExecutions` ends the attempts whose lease expired. The package knows no timer: its caller runs it, and `openTasks`'s `now` option is the clock every time, lease and timeout reads. A refusal is a result with a reason; an error from Turso or the file system rejects, as drizzle's `DrizzleQueryError` with Turso's error on `cause` when a query failed.
  - Table names, in either database, are plural (`tasks`). A table whose rows exist only for another table's rows starts with that table's name in the singular: `task_links`, `task_status_changes`, `task_executions`.
  - The server and the web app group code by feature, under the same `src/modules/<feature>/` name: Structure, below, draws both trees, and Building a feature lists the steps.
- `apps/runner` (`@sextou/runner`): the runner, its own Node process, run from source with tsx (`pnpm --filter @sextou/runner dev`) or as the bundle Vite builds into `apps/runner/dist/runner.mjs` (`build`, then `start`), with every dependency inlined but Pino and pino-pretty, which come from `@sextou/logger` as in the server's: the bundle runs with Node and those packages installed. It talks to the server only through the `runners` procedures, with a tRPC client at the URL `SEXTOU_RUNNER_SERVER_URL` names, and takes nothing from the server but its router's type, as the web app does: lint refuses any other import from `@sextou/server`. It claims a task of the assignees it serves (`SEXTOU_RUNNER_ASSIGNEES`) and runs it through the `execute` its loop takes, with a heartbeat every third of the lease the server last answered for as long as the run lasts, then completes it with how the run ended (succeeded, with the text of the tasks file it left, or failed with a reason), or as cancelled once a heartbeat says someone asked to cancel it, which stops the run, renewing the lease while it winds down; a lost lease, or one no heartbeat renewed before it ran out, stops the run and drops the task. `src/taskfile.ts` runs the default task of a Taskfile with the host's go-task, the binary its caller names (`task` on the PATH; some distributions name it `go-task`): install it once per machine. go-task and its commands run in a process group of their own, which a stop or the timeout signals whole, SIGTERM then SIGKILL after a grace, and the runner's exit kills; output a command outside the group keeps open closes a grace after go-task exits, and each line they write is an `output` record; process groups are POSIX's, so it doesn't run on Windows. Before it calls the server, `main.ts` checks that `SEXTOU_RUNNER_TASK_BIN` is go-task (its help names `--taskfile`, within `SEXTOU_RUNNER_CHECK_TIMEOUT_MS`) and exits with 1 when it isn't, and the same when tar (`SEXTOU_RUNNER_TAR_BIN`, `tar` on the PATH or a path) doesn't run (`--version`), so a runner without go-task or tar fails no task. It passes `taskfileExecute` from the same file, which downloads the repository each claim's `uses` names, at its commit, from GitHub (`SEXTOU_RUNNER_GITHUB_URL`, `<url>/<owner>/<name>/archive/<sha>.tar.gz`) into `source/`, in a folder of its own under the system's temporary folder, extracting it with that tar (`src/download.ts`) within `SEXTOU_RUNNER_DOWNLOAD_TIMEOUT_MS`, runs the Taskfile at the `uses`' path there with go-task (`SEXTOU_RUNNER_TASK_BIN`), beside the repository's files, with three variables on go-task's command line, `CONTEXT`, the task's context as JSON (`{}` without one, every `{{` written `{\u007b`, since go-task reads such a variable as a template), `WORKSPACE`, the path of `workspace/`, an empty folder beside `source/` where the run does its work, and `TASKS_FILE`, the path of `tasks.json` beside them, where the run may write the tasks that follow it, out of reach of what it does to its workspace, under `SEXTOU_RUNNER_RUN_TIMEOUT_MS` and `SEXTOU_RUNNER_KILL_GRACE_MS`, kills what the run left in its process group, reads the tasks file of a run that succeeded, never another's, and removes the folder once the run ends, without waiting for the removal. It opens the file without following a link or blocking on a FIFO and reads it only when it is a regular file no larger than `SEXTOU_RUNNER_MAX_TASKS_FILE_BYTES` (1 MiB): anything else fails the task with a reason (`tasks file: …`), while no file is no tasks. A claim whose `uses` is null fails its task with the reason `the task names nothing to run: it has no uses`, before it makes the folder or downloads anything; a folder it can't remove is logged and left. A run gets only the runner's own environment: no secret comes from the server. Each heartbeat goes a third of a lease after the last call was sent, not answered. A claim whose answer didn't arrive is sent again with the same `claimId`; a completion that got no answer or a `TIMEOUT` is sent again as it was, and one the server refused is dropped. It logs a completion with the outcome and reason the server recorded, which differ from the ones sent when a cancel arrived first or the server refused the tasks file, never the tasks file's text, then one `task created` record per task the answer names. `src/client.ts` turns each call's end into an answer the loop reads (`lease_lost`, `timeout`, `refused`, `no_answer`), so `src/runner.ts` knows nothing of tRPC. On SIGINT or SIGTERM it sends no new call, stops the run, waits for it and for the call in flight, and exits; a task it held is left to the server's lease sweep. A second signal exits at once, through `process.exit`, with 128 plus the signal's number.
- `packages/logger` (`@sextou/logger`): the Pino logger the server and the runner share. `createLogger({ level, pretty })` writes one JSON record per line to stdout, or readable lines through pino-pretty, which runs as a stream in the process rather than as Pino's transport in a worker thread; a test passes another destination. It exports Pino's level names with `silent` (`logLevels`), also from `@sextou/logger/levels`, which loads no Pino, for the apps' `config.ts`, and `@sextou/logger/testing` exports `memory()`, a destination that keeps each line a logger writes, for the apps' tests. It ships sources, not a build.
- `packages/config` (`@sextou/config`): the parsers the server's and the runner's `config.ts` share. `reader(env)` reads a variable, parsed, or its fallback when unset; `invalid` builds the error that names the variable and what it expects; `parseCount`, `parseTimeout` (1 to 2147483647 ms, the longest delay `setTimeout` takes), `parseBoolean` and `parseOneOf(values)`. Each app keeps its own `Config`, defaults and the parsers only it needs. It ships sources, not a build, and needs no Node.
- `packages/workflows` (`@sextou/workflows`): Taskfiles a runner can download from this public repository and run, each in its own folder with the files it runs, and the tests of the scripts they run. A task names the one its runner runs in its `uses`, as `thatsnotmynameio/sextou/packages/workflows/sextou/development/Taskfile.yml@<sha>`. `hello-world/` prints hello world with Python, so a runner that runs it needs `python3` on its machine; the `run-*` skills' smokes name it at the commit that added it, when it lived in `tasks/hello-world/`. `examples/create-tasks/`, for tests and smokes, not for real use, writes the task's context to `TASKS_FILE`, so a task whose context is a tasks file creates those tasks; run-runner's smoke names it at the commit that added it. A Taskfile reads the task's context with `vars: { INPUT: { ref: fromJson .CONTEXT } }` and works in `{{.WORKSPACE}}`, and quotes each value it writes into a command with `| q`, since a template is pasted into the command as text. A Taskfile whose work is more than a command or two hands the context and the workspace to a TypeScript script beside it instead, through its environment, so no value is pasted into a command, and runs it with `node` (`node main.ts`), which strips its types: only syntax Node can erase, imports that name the `.ts` file, and only `node:` modules, since the runner downloads the repository with no `node_modules`. The package's tests and coverage answer for those scripts. `git/checkout/` clones the repository its context names (`repo` and `ref`, and optionally `path` in the workspace and `server`, https only) into the workspace, a shallow fetch of that one ref checked out detached, and another Taskfile includes it to work on that repository: its Taskfile sets `CHECKOUT_CONTEXT` and `CHECKOUT_WORKSPACE` and runs `main.ts`; `settings.ts` reads and checks the context, and `checkout.ts` runs git with an argument list, exiting with 2 on an input it refuses, a path through a symlink or one that holds a repository already included, before it runs git, with 127 when git doesn't run, and with 124 once its git took longer than `CHECKOUT_TIMEOUT_MS` (5 minutes by default, from the runner's environment), which stops it: SIGTERM, then SIGKILL once `CHECKOUT_KILL_GRACE_MS` (10 seconds by default, as the runner's) went by. Its git is the program `CHECKOUT_GIT_BIN` names, from the runner's environment, a command on the PATH or an absolute path, never a relative one, which would resolve in the workspace, `git` on the PATH by default. That git reads neither the user's nor the system's git configuration, nor any `GIT_` variable of the runner's environment but `GIT_SSL_CAINFO`, nor `SSH_ASKPASS` or `NETRC`, and its `HOME` is an empty folder of its own, so no credential helper, password program or `.netrc` on the runner's machine hands a repository its secret. The checkout needs node and git; the runner checks neither. Each workflow is one action that works on what the workspace already holds and includes no other: `harness/claude-headless/` runs `claude -p` in the workspace, at `path` from its context (`.` by default, a folder that exists, such as a checkout left there), with the context's `prompt` on its stdin, `--worktree` when `worktree` is `true` or a name, and claude's options under their names in camelCase (`model`, `permissionMode`, `allowedTools` and the rest its `settings.ts` lists), each as `--name=value`, checked only for their type, since claude refuses a value it doesn't take; it ignores every other key, left for the other steps of a run. Its Taskfile sets `CLAUDE_HEADLESS_CONTEXT` and `CLAUDE_HEADLESS_WORKSPACE`, and `headless.ts` exits with 2 on an input it refuses, with 127 when claude doesn't run (`--version`), and with 124 once claude took longer than `CLAUDE_HEADLESS_TIMEOUT_MS` (an hour by default), stopped as the checkout's git is, with `CLAUDE_HEADLESS_KILL_GRACE_MS`, else with claude's code. An option's empty list is refused, since it would leave claude's default (`tools: []` every tool); an empty string says none. Its claude is the program `CLAUDE_HEADLESS_BIN` names, a command on the PATH or an absolute path, `claude` on the PATH by default, and runs with the runner's environment but for the `CLAUDE_HEADLESS_` variables, so its login or its key is the runner's; what the run hands on, a push included, is the prompt's to do. The context rules claude whole, past the workspace too (`permissionMode: bypassPermissions`, `addDir`), so a runner runs it only for tasks of people it trusts with its user's machine. `sextou/development/` chains two of them on one context: its Taskfile includes `git/checkout` and `harness/claude-headless` and runs the checkout, then claude at the same `path`, only once the checkout succeeded, and ends with the code of the step that failed. The scripts share `shared/`, which they import by a relative path, as the runner downloads the whole repository.
- `.compound-engineering/artifacts/solutions/`: documented solutions to past problems (bugs, best practices, workflow patterns), organized by category with YAML frontmatter (`module`, `tags`, `problem_type`). `ce-compound` creates it with the first one.
- `CONCEPTS.md`: the project's shared domain vocabulary (organization, workspace, task graph, data directory), relevant when orienting to the codebase or discussing domain concepts.

## Structure

```text
apps/server/
  .env.example                 every variable the server reads, with its default
  src/
    main.ts                    reads the config, starts the tasks service and the lease sweep, creates the database, listens, shuts down
    config.ts                  every setting, parsed from the environment main.ts passes
    data-directory.ts          the data directory's default on each platform
    database.ts                drizzle on Turso, and the ping health asks
    timeout.ts                 withTimeout, for a call that has no timeout of its own
    tasks.ts                   the tasks' types and the Tasks port the context carries, with no Node
    tasks-service.ts           the tasks service over @sextou/tasks, the only way into it; only main.ts imports it
    lease-sweep.ts             ends the attempts whose lease expired, on a timer main.ts starts
    server.ts                  starts @hono/node-server; resolves once listening
    app.ts                     the Hono app: CORS, then tRPC at /trpc
    trpc.ts                    the tRPC instance and the context every procedure gets
    router.ts                  each module's router under its name; exports type AppRouter
    modules/
      health/
        index.ts               the module's entry point
        health.router.ts       its procedures
        health.schema.ts       their zod schemas
      tasks/                   create, cancel, assign, link and unlink a task
      runners/                 what a runner calls: claim, heartbeat, complete
  tests/
    tasks.ts                   fakeTasks, the Tasks port a unit test's context gets
    unit/                      mirrors src/: modules/health/health.router.test.ts, lease-sweep.test.ts
    integration/               mirrors src/: database.test.ts, main.test.ts, server.test.ts, tasks-service.test.ts
apps/runner/
  .env.example                 every variable the runner reads, with its default
  src/
    main.ts                    reads the config, starts the runner, stops it on a signal
    config.ts                  every setting, parsed from the environment main.ts passes
    client.ts                  the runners procedures over tRPC, each answering an Answer
    runner.ts                  the loop: claim, execute with heartbeats, complete
    sleep.ts                   a sleep an abort ends
    download.ts                downloads a repository at a commit from GitHub and extracts it with tar
    taskfile.ts                runs a Taskfile's default task with go-task; the execute main.ts passes
  tests/
    go-task.ts                 bin and goTask, which skips a test when the host has no go-task
    archive.ts                 a repository's tarball as GitHub serves it, and an HTTP server on localhost that serves it
    server.ts                  the integration suite's global setup: the server as a child process, once per Vitest instance
    unit/                      config, client over a stubbed fetch, runner over a fake client and execute
    integration/               main.test.ts, against the server tests/server.ts starts; taskfile.test.ts, with go-task; download.test.ts, with tar
apps/web/
  .env.example                 every variable the web app reads, with its default
  vite.config.ts               loads the variables, the router plugin, the CSP
  settings.ts                  parses the variables, with their defaults
  content-security-policy.ts   the CSP plugin, given the server's URL
  src/
    main.tsx                   activates Lingui and mounts the router
    router.tsx                 the router, its context and the providers around it
    trpc.ts                    the tRPC client, its timeout fetch, the QueryClient
    routeTree.gen.ts           generated from src/routes/ by the router plugin, committed
    routes/
      __root.tsx               the layout every page shares
```

## Building a feature

A feature is a module of the server and a module of the web app under the same name, wired together by the router's type. In order:

1. **Schemas.** In the server's `src/modules/<feature>/<feature>.schema.ts`, a zod schema for each procedure's input and output.
2. **Procedures.** In `<feature>.router.ts`, `router({ <procedure>: procedure.input(…).output(…).query(…) })` (or `.mutation(…)`). The server checks the output against its schema before it sends it. A procedure takes what it needs from outside (the database, the version, a clock) from its context, never from `process` or a Node module: what it needs that the context lacks goes into `Context` in `trpc.ts`, and `main.ts` builds it. A procedure logs through `ctx.logger`, never `console`: a child of the server's logger, bound to the request's `requestId` (the `X-Request-Id` it carries, or a new one). Once released, a procedure's input and output stay backward compatible, since a web build may call a server of another version.
3. **Entry point.** `index.ts` exports the router, and whatever another module needs.
4. **Registration.** `src/router.ts` adds the module's router under the feature's name, so the procedure is `<feature>.<procedure>`, at `/trpc/<feature>.<procedure>`.
5. **The web module.** In the web's `src/modules/<feature>/`, the components, which call the procedure through TanStack Query: `useQuery(trpc.<feature>.<procedure>.queryOptions(…))`, or `mutationOptions` for a mutation. The component handles each way the request can end: the data, an error the server sent (a `TRPCClientError` with `data`), no answer from the server (a `TRPCClientError` without `data`: the connection failed, the request timed out, or something else answered) and still pending. Shown text goes through Lingui, colors and fonts come from `theme.css`'s tokens, and `@sextou/ui`'s components take data and callbacks as props.
6. **The route.** A file in the web's `src/routes/` for each URL, `createFileRoute('<path>')({ component })`, whose component passes the client from `Route.useRouteContext()` to the module's component.
7. **Settings.** Each new setting is an environment variable with a default: the server's are `SEXTOU_SERVER_*`, read in `config.ts` with a parse that names the variable on an invalid value; the web's are `SEXTOU_WEB_*`, parsed in `settings.ts` and written into the bundle by `vite.config.ts`'s `define`. List each in its app's `.env.example` with its default, and say there which settings must agree with another app's. Every web variable is public, since the bundle carries it: a secret is read only by the server's `config.ts`, has no default in code, and appears in `.env.example` with an empty value.
8. **Timeouts.** Every call that waits on the network or on another process has a timeout, which is a setting too. The web's requests get the client's (`SEXTOU_WEB_REQUEST_TIMEOUT_MS`), the server's database queries the database's (`SEXTOU_SERVER_DATABASE_TIMEOUT_MS`), the tasks database's writes their own (`SEXTOU_SERVER_TASKS_TIMEOUT_MS`, checked inside the write, since a write a timer gives up on may still commit), and anything else `withTimeout` from `src/timeout.ts`. A timeout on the server stays below the web's request timeout, so the server answers before the web app gives up.
9. **Tables.** The first feature that adds a table to the server's database brings drizzle-kit, on drizzle-orm's release candidate, with the schema and the migrations the server applies on start. A transaction runs through drizzle's `db.transaction()`, every query inside it on its `tx`: one on `db` waits for the lock the transaction holds, and hangs (`.compound-engineering/artifacts/solutions/best-practices/turso-behaves-differently-from-sqlite.md`).
10. **Tests**, at the levels the Tests section defines:
    - A procedure: unit, through `createCallerFactory(<feature>Router)` with a context the test builds.
    - What only HTTP shows (the status, CORS, the error's shape): unit, through `createApp(…).request(…)`.
    - Code that reaches the disk, a listening port or a child process: integration, its file listed in `integrationOnly` with the reason.
    - A page: unit, rendering `createAppRouter({ serverUrl, requestTimeoutMs, history: createMemoryHistory(…) })` in a `RouterProvider`, with `fetch` stubbed (`vi.stubGlobal`) for each way the request can end.
    - A page against the real server: integration, with the server started as a child process, as `tests/integration/modules/health/health-page.test.tsx` does.
11. **Imports.** Lint enforces three rules, in `.ts` and `.tsx` files alike: a module reaches another module only through its `index.ts`, in the server and in the web app; the web app and the runner import from the server only types, written as a whole `import type` statement from `@sextou/server/router` (lint refuses `import { type … }` everywhere, since it can leave a side-effect import behind); and nothing in `apps/web` or `packages/ui` imports `electron`.

## Desktop security

The window runs remote content, so a script injected into the web app, or a compromised deploy, must not get past it. Each item of [Electron's security checklist](https://www.electronjs.org/docs/latest/tutorial/security), and where it stands:

- **Secure content only:** packaging fails when `SEXTOU_WEB_URL` is set and isn't https (`vite.main.config.mts`). Development loads `SEXTOU_WEB_URL`, `http://localhost:5173` by default.
- **No Node integration, context isolation, sandbox:** stated in the window's `webPreferences` (`src/main/main.ts`), though they are Electron's defaults.
- **Permission handler:** `setPermissionRequestHandler` and `setPermissionCheckHandler` deny every permission on the default session, without a prompt. A feature that needs one allows only that one.
- **`webSecurity`, `allowRunningInsecureContent`, experimental features, `enableBlinkFeatures`:** left at Electron's safe defaults; never set them.
- **Content Security Policy:** a meta tag that `apps/web/content-security-policy.ts` adds to the built page, so browsers get it too. The page connects only to its own origin and to the server's (`SEXTOU_WEB_SERVER_URL`). Not in development, where the dev server needs inline scripts and styles. A meta tag can't set `frame-ancestors`; that waits for the hosting headers.
- **Navigation and new windows:** `src/main/link-policy.ts` decides every URL, applied by `will-navigate`, `will-redirect` and `setWindowOpenHandler`. The window stays on the web app's origin, links to other sites open in the default browser, and the app never opens a second window.
- **`shell.openExternal`:** it gets only `http`, `https` and `mailto` URLs, through the link policy. Other schemes, which would launch local files or other apps, open nothing.
- **`<webview>` (`allowpopups`, verifying its options):** the tag is off by default and unused.
- **Current Electron:** a standing practice. Upgrade Electron when a release lands.
- **IPC sender validation:** there is no IPC yet. Validate the sender in the first handler that lands.
- **`file://`:** unused; the window loads the web app by URL and the error page as a `data:` URL.
- **Fuses:** set in `forge.config.mts`.
- **Electron APIs exposed to web content:** the preload exposes nothing. Expose only narrow functions through `contextBridge`, never Electron modules.

## Tests

Tests are organized by package, then by level. Each package has only the levels its code needs, and each pair of package and level runs on its own.

**Where they live.** Out of `src/`, in the package's `tests/<level>/`, which mirrors `src/`: the unit test of `src/modules/health/health.router.ts` is `tests/unit/modules/health/health.router.test.ts`, the integration test of `src/database.ts` is `tests/integration/database.test.ts`. The folder names the level, so every test ends in `.test.ts(x)`. The web's tests of its build modules, beside `vite.config.ts`, sit at the top of `tests/unit/`. A helper that tests share sits at the top of `tests/` (`packages/ui`'s `render.tsx`). The stories stay beside their component in `src/`, since Storybook shows them too.

**Levels.** Decide a new test's level by what it reaches:

- **unit** (`tests/unit/`): one unit of a package through its public API, in one process, touching neither the disk nor the network. Real in-memory collaborators are fine, an in-memory SQLite database (`':memory:'`) included. Runs in Node, or in jsdom for `apps/web` and `packages/ui`.
- **integration** (`tests/integration/`): real parts working together: the package with a real resource (a file on disk, a server listening on localhost, a child process), or two or more sextou packages used for real, whether the test imports the other package or the code under test does.
- **component** (the stories, `*.stories.tsx`): a UI component rendered in a real browser, Chromium through Playwright; each story must pass its `play` function, which checks what needs a real browser (layout, focus, truncation). Only `packages/ui` has one.
- **e2e**: a flow the way a person uses sextou, the web app in a browser or the desktop window talking to a real server process, acting only through the interface and replacing no part with a test double. None exists yet; the first one must meet this.

Every package has a unit suite, an integration suite wherever its code reaches a real resource or another sextou package, and a component suite only where it has UI to render. Today `apps/runner`, `apps/server`, `apps/web`, `packages/tasks` and `packages/workflows` have an integration suite, and `packages/ui` a component suite. `apps/web`'s integration suite renders the health page against the server started as a child process, and answers for no file: its unit suite already reaches each one at the floor.

**Suites.** Each suite is its own Vitest config, because Vitest reads coverage only from the config at the root of a run: `vitest.config.ts` is the unit suite, beside `vitest.integration.config.ts` and, in `packages/ui`, `vitest.component.config.ts` (`.mts` in `apps/desktop` and `apps/server`). Each Vitest project is named `<pkg>/<level>` (`tasks/unit`, `ui/component`). The root `vitest.config.ts` runs every unit and integration suite, never the component suite, and sets no coverage. Each suite is a `test:<level>` script in its package's `package.json`; `test:mutation`, beside them, is Stryker's run, not a level.

**Coverage.** Each suite must reach 90% (lines, branches, functions, statements) in every source file it answers for, on its own: each `test:<level>` run fails below it. A package's unit config lists, in `integrationOnly`, the files its integration suite answers for; the unit suite answers for every other file, so a new file belongs to it until it is listed. Some files have no unit test on purpose, each with a comment beside the `integrationOnly` list saying why:

- `apps/server`'s `database.ts` takes `':memory:'` or a path, and neither kind of case alone reaches the floor, so its in-memory cases sit in the integration test beside the cases on a file, with the same comment at the top of that test.
- `packages/tasks`'s `open-tasks.ts` and `graph.ts`: opening the graph reads its migrations from disk, even for `':memory:'`, so every test that opens one is an integration test. Its unit suite answers for the input schemas and the statuses. `schema.ts` answers to neither suite and is left out of mutation: only drizzle-kit runs its checks, indexes and foreign keys, outside what coverage sees, and the drift test guards them.
- `packages/tasks`'s `owner-only.ts` sets the modes of files on disk.
- `apps/server`'s `server.ts` listens on a port, and its `main.ts` creates folders on disk and opens the database.
- `apps/runner`'s `main.ts` runs the runner against the server, which its test starts as a child process, its `taskfile.ts` runs go-task as one, and its `download.ts` runs tar as one, on what an HTTP server on localhost serves.
- `apps/server`'s tasks service runs `@sextou/tasks` for real, two sextou packages together, even on `':memory:'`.
- `packages/workflows`'s `git/checkout/checkout.ts` runs git as a child process, against a git server on localhost, `harness/claude-headless/headless.ts` runs a fake claude the test writes to disk, `shared/run.ts` runs both, and `shared/workspace.ts` reads folders on disk through both; their tests call them in the test's own process, so coverage and Stryker see them. A script's `main.ts`, which only calls its module with the process's environment, answers to neither suite and is left out of mutation; its Taskfile test runs it with node.

The desktop suite covers the main process's pure modules in Node; `main.ts` imports Electron and stays out of it. The web's suites cover `src/` and the build's own modules beside `vite.config.ts`, and leave out `src/main.tsx`, which only mounts what the tests render, and the generated `src/routeTree.gen.ts`.

**Running part of it.** `pnpm --filter <package> test:<level>` runs one level of one package and `pnpm test:<level>` that level everywhere. To run one module, filter by its path through the root config: `pnpm exec vitest run --project 'server/*' modules/health`. It reports the tests and never fails on coverage, which only the full run of a level judges; a path passed to `test:<level>` fails on every file it leaves out. A component filter runs inside `packages/ui` with `pnpm exec vitest run --config vitest.component.config.ts <path>`. Install Chromium once per machine with `pnpm --filter @sextou/ui exec playwright install chromium`. `apps/runner`'s `taskfile.test.ts` and `main.test.ts`, and `packages/workflows`'s `Taskfile.test.ts`, run go-task as `task` on the PATH, and skip their tests that need it when there is none, as in the organization's `typescript.yml`; `test:integration` then fails on coverage.

**Mutation.** StrykerJS changes the code one mutant at a time and runs the package's unit and integration suites against each. `stryker.parent.conf.json` at the root holds what every package shares, and each package's `stryker.config.mjs` adds only its own: the Vitest config it runs (`vitest.mutation.config.ts` gathers both suites where a package has two) and the files it leaves out. Stryker fails the run when the package's score is below 80% (`thresholds.break`); it has no threshold per file. A mutant that changes no behavior gets `// Stryker disable next-line <mutator>: <reason>`, never a lower floor. Code excluded from coverage is excluded from `mutate` too. Three things to know:

- Tests sit at the top level of their file, with no `describe`. Stryker 10.0.0's Vitest runner names a test inside a `describe` the way Vitest 4 did, so under Vitest 5 that test runs for no mutant and every mutant only it would kill survives (issue #54 brings `describe` back once a release fixes it). The file groups its tests; `test.each` runs one test over several values, `test.skipIf` skips one on a platform, and a helper the test calls sets up what only some tests need.
- Stryker runs the tests in worker threads, where `os.homedir()` ignores a changed `HOME`: mock `homedir` from `node:os` instead, as `apps/server`'s `tests/integration/main.test.ts` does.
- `stryker.parent.conf.json` names a `tsconfigFile` that doesn't exist: Stryker rewrites `tsconfig.json` in its sandbox through TypeScript 6's API, which TypeScript 7 lacks (stryker-js#6111).

**Writing tests.** For people and agents alike:

- Before writing tests, read the source file, its tests under `tests/` and the package's Vitest configs, and follow their conventions.
- Test the contract: inputs, return values, side effects and errors, through the public API. A test that breaks when the internals change but the result stays the same tests implementation.
- One behavior per test, with a name that states its subject and the behavior (`openTasks on a file rejects a file that is not a database`); an "and" in the name means two tests.
- Arrange, act, assert.
- Every assertion checks a real result. A test that only checks that nothing throws, that something is defined, or what a mock received does not count: Stryker reports the mutants it lets through as survived.
- Cover the boundaries, the error paths and every side of each condition: empty input, `null` and `undefined`, limits, failed requests, empty lists. If a real caller can trigger it, test it.
- Prefer real implementations when they are fast and reliable. Mock only what is slow, flaky or has side effects the test can't control, never the thing under test. Use fake timers for time.
- Each test sets up its own state and passes in any order; mocks are restored after each test.
- Use Vitest's APIs (`vi.fn`, `vi.mock`), with the typed form `vi.mock(import('./module'))`.
- A bug fix starts with a failing test that reproduces the bug, so the fix changes the code, not the test.
- Run tests with `vitest run`, never in watch mode, and read the coverage and mutation results before finishing.
- Property-based tests are an option for functions with wide input ranges.

## Git hooks

`pnpm install` sets up husky's hooks, in `.husky/`. Never skip or disable them: no `--no-verify`, no `HUSKY=0`. When a hook fails, fix what it reports.

- `pre-commit`: gitleaks scans the staged changes for secrets, then lint-staged runs `oxlint --fix` and `oxfmt` on the staged files and stages their fixes. Install gitleaks once per machine.
- `commit-msg`: the subject must be a Conventional Commit, `type(scope): description`. CI checks a pull request's title by the same rule (`pull-request / title`).
- `pre-push`: every pushed branch must contain the remote's latest `main` (rebase onto it otherwise), then `pnpm typecheck` and `pnpm test:unit` run.
- `post-merge`: runs `pnpm install` when a pull changes `pnpm-lock.yaml`.

## CI

- On pull requests, the organization's ruleset runs `typescript.yml` (thatsnotmynameio/github-actions) as `tnmn.io: typescript`; `.github/workflows/ci.yml` runs it on `main`, pinned by SHA with the version as a comment. It installs under the organization's pnpm policy (versions at least a day old, no trust downgrade), checks every tracked `tsconfig.json` with `strict` on, runs oxfmt, oxlint (type-aware, TypeScript 7) and knip, then `pnpm run build`.
- `.github/workflows/checks.yml` runs this repository's checks on pull requests and on `main` as one chain, each job starting only once the ones before it passed: lint, then every package's unit suite, then every integration suite, then every component suite, then mutation. A job after `unit` runs on `!failure() && !cancelled()`, since a level no package has is skipped and would otherwise skip every job after it; `packages` fails on a `test:<level>` the chain doesn't name, so a new level needs a job of its own there. The title, CodeQL and Scorecard stay out of the chain: the title check runs again whenever the title is edited, which in the chain would rerun every test; CodeQL is required, and a required check skipped by a failed job before it counts as passed; and code scanning tells CodeQL and Scorecard apart by workflow file and job.
  - `lint / gates` runs oxlint with `.oxlintrc.gates.json`, 38 rules that most large open-source TypeScript and React projects enforce, each at `error`, and fails on any finding. One of them, `eslint/no-console`, refuses `console` everywhere but test files (`*.test.ts`, `*.test.tsx`): code logs through a logger. The organization's `typescript.yml` doesn't read that file. Not required in the ruleset yet. To run it locally: `pnpm exec oxlint -c .oxlintrc.gates.json .`.
  - The tests: one check per pair of package and level (`tasks / unit`, `ui / component`), each judging its files at 90%, and one per package for mutation (`tasks / mutation`), failing below 80% of the package's mutants killed. Its `packages` job, which waits for nothing, builds one list per level and one for mutation from each workspace package's `test:<level>` and `test:mutation` scripts, so a new package needs no change to the workflow. The level jobs share their steps through a YAML anchor. Each level's job uploads its coverage report to Codecov through OIDC, flagged `<package>-<level>`, and `codecov.yml` makes Codecov's statuses informational, so the 90% floor stays the gate, and carries each flag forward, so a pull request that skips a package's level shows that flag's last coverage. Only a `component` level installs Chromium, and only the runner's jobs install go-task, the release checked against its checksum. None is required in the ruleset yet. A level waits for the one before it in every package, since a matrix job waits for the whole matrix. Mutation runs every mutant of every package on each push to `main`. On a pull request, `packages` lists for each level and for mutation only the packages its changes reach. A package's changes reach the package itself and the packages that depend on it through a `workspace:` dependency, directly or not, as pnpm's `[<since>]` filter selects them against the base (`...[HEAD^1]`). For mutation, a package that holds a changed file runs what changed since the newest result in the Actions cache, the pull request's own or else `main`'s (Dependabot's pull requests always start from `main`'s), and a dependent runs every mutant, since the incremental run compares only its own files. A changed file outside every package (the lockfile, the root `tsconfig.json`, `stryker.parent.conf.json`, anything in `.github/`) runs every package, mutation in full; a change only to files no suite reads (Markdown, `.claude/`, the linters' and Codecov's settings) runs no suite and no mutation. A package left out has no check for that level on that pull request, which a required check would block on. The organization's `typescript.yml` still runs the unit and integration suites through the root config, so a pull request runs them there for every package, whatever it changes, until this moves there.
- `.github/workflows/pr-title.yml` runs on pull requests: `pull-request / title` (amannn/action-semantic-pull-request) fails when the title isn't a Conventional Commit with one of the types `.husky/commit-msg` allows, and, on a pull request of one commit, when that commit's subject isn't, since the squashed commit on `main` takes the title, or the subject of a lone commit (`COMMIT_OR_PR_TITLE`, set for the organization in thatsnotmynameio/admin). Dependabot's titles pass as `build(deps): …` and `ci(deps): …`. Not required in the ruleset yet.
- `.github/workflows/security.yml` runs CodeQL on pull requests (`codeql / javascript-typescript`, `codeql / actions`, required by thatsnotmynameio/admin's `.github/repos/sextou.yml`): keep the job named `codeql`. `security-main.yml` runs grype and zizmor on `main`.
- `.github/workflows/scorecard.yml` runs OpenSSF Scorecard (`ossf/scorecard-action`) on pull requests, on `main` and weekly, and when a branch protection rule changes; its results go to code scanning, where each check below 10 is an alert. On `main` it runs every check through GitHub's API and publishes the score to `api.scorecard.dev`; on a pull request it runs only the checks that read files, and publishes nothing. It never fails on a score, and the organization's code scanning ruleset blocks only on CodeQL's alerts. Publishing makes `api.scorecard.dev` check the workflow: no `env`, `defaults` or `run` step, `id-token: write` only in the job that runs the action, and only the actions on its list. Not required in the ruleset.
- Its settings come from the base commit: `.oxlintrc.json`, `.oxfmtrc.json`, `knip.json`, the root `tsconfig.json` and `pnpm-workspace.yaml`'s exceptions (`allowBuilds`, `trustPolicyExclude`, …) apply once they merge.
- `main` takes changes only through pull requests, merged by squash. No force push.
